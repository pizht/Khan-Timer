# Internationalisation (i18n) design and operations

This document describes how the extension is localised: **English (`en`) is the default language,
the source of truth for message keys and the fallback language; Simplified Chinese (`zh-CN`) is a
translation.** Only those two ship today; the steps to add a third are at the end.

The audience here is maintainers. The user-facing explanation is in the
[user guide → Settings](../README.md#settings).

---

## 1. Why `chrome.i18n` does not do all of the work

Manifest V3 ships `_locales/` plus `chrome.i18n.getMessage()`. This project uses it **only where
nothing else can**, and routes everything else through its own message catalogs. The reasoning:

| Concern | `chrome.i18n` | Own catalogs (this design) |
|---|---|---|
| Extension name / description localisation (extensions page, stores) | ✅ the only mechanism | ❌ cannot reach it |
| Static copy inside HTML | ❌ MV3 does **not** support `__MSG_key__` in HTML (it only works in the manifest and CSS) | ✅ `data-i18n` + runtime substitution |
| Switching language inside the app | ❌ no "force this language" API; it can only follow the browser UI language | ✅ stored in settings, changeable at any time |
| Unit tests (vitest/jsdom) | ❌ no `chrome.i18n`, so every test would need a mock | ✅ plain functions, tested directly |
| Missing translation | ❌ silently returns an empty string at runtime | ✅ compile-time error |

Therefore **`_locales/` only contains the extension name and description** (`extName` / `extDesc`),
and all interface copy goes through `src/i18n/`. The two sets do not overlap, so no sentence is
maintained twice.

## 2. Layout and responsibilities

```text
src/i18n/
├── en.ts       # English catalog: the single source of truth. MessageKey = keyof typeof en
├── zh-CN.ts    # Simplified Chinese: Record<MessageKey, string>; one missing key fails the build
├── index.ts    # t() / setLocale() / resolveLocale() / plural selection / interpolation
└── dom.ts      # localizeDom(): translates the data-i18n nodes in popup.html
public/_locales/
├── en/messages.json      # default_locale; extension name and description (English)
└── zh_CN/messages.json   # the same (Chinese)
```

### Key naming

Keys are prefixed by the area of the UI they belong to, which makes them easy to find and to add or
remove: `app.*` (shared), `overlay.*` (floating panel), `summary.*` (end-of-exercise card),
`event.*` (panel footer / the popup's "last event"), `warning.*` (degradation warnings),
`popup.*` (the popup).

### Placeholders and plurals

- Placeholders are written `{name}` and interpolated by `t()`:
  `t('summary.questionNumber', { number: 3 })`. When an argument is missing the **placeholder is left
  as written** (`Question {number}`) so the bug is visible instead of rendering as nothing.
- Messages that vary with a count come in `_one` / `_other` pairs; the call site passes `count` and
  `Intl.PluralRules` picks the form for the language:

  ```ts
  'summary.totalAll_one': '{count} question · {total} total',
  'summary.totalAll_other': '{count} questions · {total} total',
  ```
  ```ts
  t('summary.totalAll', { count: rows.length, total: formatDuration(totalMs) })
  ```

  `t()` takes the **base name** (`summary.totalAll`). `PluralKey` is derived from the catalogs: as
  soon as a catalog has `X_one` / `X_other`, `X` becomes usable as a key, and a base name without
  plural siblings is rejected by the compiler. Chinese has a single plural category (it always hits
  `_other`), so its `_one` and `_other` strings are identical — both exist to keep the type fully
  covered and to remind translators that the key depends on a count. Lookup order is "the target
  category in this language → `_other` in this language → `_other` in English", so adding a language
  with several categories (Russian, say) still degrades to a grammatical sentence instead of leaking
  a key name when `_few` is missing.

- **Never put HTML in a message**: `t()` returns plain text; `overlay.ts` / `summary-view.ts` build
  their own templates and call `escapeHtml` where needed.

## 3. How the language is chosen

```
settings.language = 'auto' | 'en' | 'zh-CN'      (default 'auto')
        │
        ├─ 'en' / 'zh-CN' ──────────────► use it
        └─ 'auto' ─► chrome.i18n.getUILanguage() ─► navigator.language ─► normalise
                                                          │
                            'zh*' → zh-CN ; 'en*' → en ; anything else → en (fallback)
```

- Normalisation looks only at the language prefix and drops the region: `en-US` / `en-GB` → `en`;
  `zh-Hans-CN` / `zh-TW` → `zh-CN`.
- **An unknown language always falls back to English** (`FALLBACK_LOCALE`), because the primary
  audience is English-speaking; a single missing key in a translation also falls back to English.
- The learner can pin a language in the popup's `Language` field; the value is stored in `settings`
  inside `chrome.storage.local`. When reading old values, `sanitizeSettings` maps anything
  unrecognised to `'auto'` (`sanitizeLanguage` in `storage.ts`), so **settings written by older
  versions need no migration**, including a missing `language` key.

### What happens to text already on screen after a switch

This is the easiest place to get it wrong. There are three cases:

1. **Static copy in `popup.html`**: `data-i18n="<key>"` plus a fresh `localizeDom()` pass. MV3 does
   not allow `__MSG_` in HTML, so this is the only route. The English written in the HTML is the
   source and the fallback copy, and `tests/i18n.test.ts` asserts it matches `en.ts` exactly so the
   two cannot drift.
2. **Labels belonging to the panel / card** (title, buttons, `aria-label`, and the "Done" / "Paused"
   badges drawn by CSS pseudo-elements): `OverlayView.applyLanguage()` and
   `SummaryView.applyLanguage()`. The pseudo-element copy is updated by rebuilding the
   `<style>` element's `textContent` — it is not a DOM text node, so changing text nodes cannot
   reach it.
3. **The panel footer's status line and degradation warnings**: these **do not store a translated
   string**, only a `MessageRef = { key, params }`, and are translated when they are actually
   painted (the `lastEventText` / `warningText` getters inside `render()`). Otherwise the line would
   stay in the old language until the next detection event happened to overwrite it.

`controller.ts` listens to `chrome.storage.onChanged`: when `language` changes it calls `setLocale()`
and has the panel and card run `applyLanguage()`, so **no page refresh is needed** and a page mid-way
through a question re-renders immediately. The timing state machine is not involved at all (see
section 5).

## 4. Verification

| Mechanism | What it covers |
|---|---|
| `pnpm run typecheck` | missing keys in a translation, misspelled key names, wrong `PluralKey` usage |
| `tests/i18n.test.ts` | identical key sets across catalogs, no empty strings, no "copied the English" non-translation, placeholders matching on both sides, plural selection per language, fallback and normalisation, every `data-i18n` key exists and matches English, tagged nodes are leaves |
| `tests/popup.test.ts` | the language selector: options, **re-rendering copy** after a switch (including data-generated status lines and record counts), `<html lang>`, writing to storage, reuse on the next open |
| `tests/overlay.test.ts` | switching language in the panel: title / buttons / `aria-label` / **CSS pseudo-element badges** |
| `tests/summary-view.test.ts`, `tests/controller.test.ts` | assert against the message catalogs rather than a specific UI language |
| `verify-dist.mjs` | `_locales/` must declare `default_locale` (otherwise browsers refuse to load the extension), every `__MSG_*__` in the manifest resolves to non-empty copy, the store description is ≤ 132 characters, and `dist/` allows `_locales/**/messages.json` |
| `scripts/verify-extension.mjs` | real Edge: the panel renders in the expected language (check 1b) plus a **two-way** end-to-end check of the language selector (choose English → the popup *and* the in-page panel both change copy; switch back to "follow the browser" → both revert) |
| `scripts/verify-practice-switch.mjs` | real Edge: pins `settings.language` to `zh-CN` before it starts |

### Why the two end-to-end scripts pin Chinese

They read **Chinese copy** (`正计时` "Count up", `继续` "Resume", `第 N 题` "Question N",
`数据缺失` "No data", `加试` "Bonus", `暂停 0:17` "Paused 0:17", …). Once the UI language follows the
browser, those assertions would depend on the machine running them, so:

- `verify-extension.mjs`: adds the `--lang=zh-CN` launch flag **and** writes `language: 'zh-CN'`
  through the extension's own storage (`pinLanguage()`), because `--lang` does not take effect on
  every platform. Check 1b asserts the **panel title** (the thing actually read), not the browser
  language.
- `verify-practice-switch.mjs`: uses `pinLanguage()` only, because `--login` reuses an existing
  profile that carries a locale, and a command-line flag is not guaranteed to beat a profile
  preference.
- `verify-startcard-flash.mjs` asserts no UI copy at all (it only looks at the timer digits and
  panel visibility), so it does not need a pinned language.

### Manual verification

1. Open the popup and set `Language` to `English`: the labels, status line and history switch to
   English immediately, and `<html lang="en">`.
2. Make the same switch on an **already open, currently timing** Khan Academy page: the floating
   panel's title, buttons, the `Limit` / `Progress` meta row and the footer's "last event" should all
   switch to English at once, with no page refresh. In developer mode you can also see the
   end-of-exercise card follow along.
3. Switch back to "follow the browser": with a Chinese browser UI it should return to Chinese.

## 5. Boundaries and non-goals

- **Code comments, `console.warn` and raw diagnostic data are not translated.** Field *names* in the
  diagnostics block (developer mode) are translated, but its *values* (selector strategy names,
  `data-testid` values, question identities) are left alone because they are identifiers used for
  cross-checking.
- **Site text is not translated.** The page-text checks in `site-profile.ts` (for example the privacy
  banner's `cookie|privacy|隐私`) are there to **match the page**, not to label the UI, and must never
  follow the interface language. Whether an answer was right is taken from the progress state
  segment, not from feedback wording, so detection is independent of the interface language.
- **`Intl` is used only for plurals and time formatting.** Record timestamps are formatted with
  `toLocaleTimeString(getLocale())`; durations (`m:ss`) are language-independent and are not
  localised.
- **Store listings** (names, descriptions and screenshot captions in the Chrome Web Store / Edge
  Add-ons) are entered in the developer console; `_locales` cannot reach them.

## 6. Adding a language (Japanese, say)

Four steps, all guarded at compile time or by tests:

1. **Add the translation**: copy `src/i18n/zh-CN.ts` to `src/i18n/ja.ts` and change it to
   `export const ja: Record<MessageKey, string> = { ... }`. A missing key or a misspelled key name
   makes `pnpm typecheck` fail.
2. **Register it** in `src/i18n/index.ts`:
   - add a `ja` entry to `CATALOGS` (`SUPPORTED_LOCALES` is derived from it, so there is nothing else
     to maintain);
   - add a prefix check to `normalizeLocale()` (`lower.startsWith('ja')`).
3. **UI and manifest**:
   - add `'ja'` to the `Locale` union in `src/types.ts`;
   - add an option to the language dropdown in `public/popup.html`:
     `<option value="ja">日本語</option>` (a language name is written in its own language and gets no
     `data-i18n`);
   - add `public/_locales/ja/messages.json` (copy the `en` file, translate `extDesc`; `extName` is a
     product name and stays untranslated).
4. Run `pnpm run verify`: `tests/i18n.test.ts` automatically includes the new catalog in the
   "identical key sets / no empty strings / identical placeholders / actually translated" checks, and
   `verify-dist.mjs` lets the new `_locales/ja/messages.json` through.

If translations are supplied by someone who does not work in TypeScript, a build-time codegen step
(`locales/ja.json` → `src/i18n/ja.ts`) can be added on top. With only two languages that layer is not
worth it yet.
